<objective>
Rescope `appo apps update` to the three user-editable fields (name, url, icon) and
add the new `ops.setIcon` transport for the apps-web-app icon endpoint. The icon is
set via its own route — `POST /api/v1/apps/{app}/icon` with body `{ "icon_url": "<https image URL>" }`,
returning a flat `200 { "icon_url": "..." }` — and takes an https image URL (mirrors
`apps create --url`), NOT a file upload. The two metadata flags (`--meta-name`/`--meta-desc`)
are removed because the v1 PATCH surface now silently ignores all fields except
`name`/`base_url`. When both content (name/url) and `--icon` are given, PATCH runs
first, then the icon POST. An icon SSRF/validation reject (422) rides the existing
`renderError` else-branch — it is a plain Laravel validation envelope, NOT a
`prerequisite_failed` block.

Purpose: Satisfy SC-3 (`apps update` = name/url/icon; `--meta-*` removed; `--icon`
via the icon endpoint).
Output: New `ops.setIcon` in `src/ops.mjs`, rescoped `apps update` branch + `apps create`
metadata drop in `src/cli.mjs`, reshaped `test/integration/write-verbs.test.mjs`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI → v1 API | User PAT crosses here; `--icon` URL is user-supplied and passes through unmodified to the server |
| `--icon` URL → server fetch | The server (SetIconFromUrl) fetches the supplied URL — the SSRF-sensitive boundary, enforced entirely server-side |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-04 | Information Disclosure / Tampering (SSRF) | `--icon` URL fetched by the server | transfer | The CLI passes the raw URL to `POST .../icon` and performs ZERO client-side validation. ALL SSRF defense (https-only, private-IP reject, DNS-rebind pin, no-redirect, ≤5 MB, mime allow-list) is enforced server-side in `SetIconFromUrl` [VERIFIED: apps-web-app 190-02]. Client-side checks are explicitly avoided to prevent divergence. A rejected URL returns 422, surfaced via `renderError`. |
| T-07-05 | Information Disclosure | PAT leaking into the icon 422 error line | accept | `renderError` prints only `err.message` (server validation text), never the token; `apiFetch` 401 stays token-free. The `--icon` URL is user-supplied (not a secret) and safe to echo. Unchanged invariant — low risk. |
| T-07-06 | Tampering | Empty/garbage `--icon` value POSTed | mitigate | The `typeof flags.icon === 'string' && flags.icon` guard makes a bare `--icon` (parsed as boolean true) a usage error (exit 2) — no empty-body POST is issued. |
</threat_model>
